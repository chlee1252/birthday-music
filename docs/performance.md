# 검색 속도 검증 — 2026-10-25

한국에서 프로덕션 URL을 fetch하여 HTML 본문 수신 완료까지 측정했다. 브라우저 이미지 로딩/LCP 측정값은 아니다. 표본이 적고 외부 제공처 상황에 따라 달라진다.

## 이전 배포
- 2014-01-01, 팝송 카테고리 선택: 50,782ms, 일부 Wikidata TIMEOUT.
- 같은 날짜 한국 노래 캐시 응답: 1,333ms.
- 기본 함수 리전 iad1.

## 개선 후 배포
- 리전 icn1 확인. 최초부터 한국/팝 모두 조회하므로 이전 선택 장르 조회보다 조회 범위가 넓다.
- 2014-01-01: 11,045ms / 10,264ms. 일부 팝송 조회 TIMEOUT은 남아 있으며, 실패를 성공으로 캐시하지 않으므로 재조회도 약 10초. 기존 팝 조회 대비 약 78% 감소했지만 완전 성공한 결과의 속도로 해석하면 안 된다.
- 2014-04-07: 최초 10,387ms 일부 TIMEOUT, 다음 10,936ms 전부 성공, 이후 342ms / 57ms.
- 1995-11-27: 최초 7,617ms, 다음 79ms, 오류 없음.
- 모든 측정 응답 HTTP 200. UI는 각 데이터 소스 실패를 별도로 표시한다.

## 원인과 변경
- Wikidata 25초 타임아웃을 재시도하여 약 50초 대기하던 동작을 10초 단일 시도로 변경.
- 정상 빈 멜론 응답에서도 Apple 검색을 연달아 실행하던 불필요한 fallback 제거. 실제 요청 실패 시 대체 API 유지.
- Next Data Cache로 성공한 원천 응답, 역대 차트, 전체 검색을 24시간 재사용. 실패/부분 결과는 공유 캐시에서 제외.
- 모든 카테고리/지역을 병렬 조회하며 칩은 클라이언트 상태 전환만 수행.
- 미국 함수 리전에서 서울로 이동. 역대 팝 차트 검증 기록은 필요한 필드만 캐시.

## 남은 한계
실시간 외부 데이터 조회를 모두 기다리는 정책상 첫 조회는 수 초 걸린다. 특히 1월 1일 해외 발매 SPARQL 쿼리는 여전히 제한 시간 내 완료되지 않을 수 있다. 데이터 누락을 “해당 곡 없음”으로 바꾸지 않는다. 더 낮고 일정한 첫 조회 시간을 위해서는 별도 수집 작업과 생일/발매일 인덱스를 가진 영속 데이터 저장소가 필요하다.

## 팝송 카탈로그 확대 이후 재검증
2026-10-25 Apple 우선 조회와 국제 등재 근거를 추가한 후, 발매 후보 아티스트들의 인기곡 검증을 한 요청으로 묶었다.
- 2014-10-27 전체 검색: 최초 36,649ms(일부 외부 TIMEOUT), 다음 3,605ms(오류 없음). Style 등 5곡 유지. 이 날짜의 초기 조회 비용이 커졌으므로 과거 7~11초가 모든 날짜의 보장값은 아니다.
- 같은 날짜 exact/pop 단독 재시도: 2,488ms, 5곡, 오류 없음.
- 2014-01-01 same/pop 단독 재시도: 10,280ms, Wikidata TIMEOUT 유지.
- UI 카테고리 재시도는 전체 화면이나 다른 카테고리의 재조회 없이 수행한다. 추가 원천 조회가 필요한 첫 검색의 지연은 영속 날짜 인덱스 없이 완전히 없애지 못했다.

## 비동기 대기 개선과 로딩 안내 — 2026-10-26
기존에도 상위 카테고리는 Promise.all로 병렬 조회했으나, 하위 MusicBrainz/Apple 큐가 이전 응답의 완료까지 기다렸다. 이제 요청 시작 간격(MB 1.1초, Apple 3.1초)을 지키면서 응답은 겹쳐 기다린다. 재시도 역시 동일 시작 간격 제한을 적용한다. 제한은 기존처럼 인스턴스 단위이다.

팝송 인기 근거와 곡 조회를 병렬로 시작한다. 카테고리별로 검증된 서로 다른 곡 10개를 확보하면 추가 후보 작업을 중단한다(이미 진행 중인 최대 3개는 완료). 메타데이터 25초 및 반복 타임아웃 대기를 줄이고, 실패는 기존 partial/unavailable로 유지한다. 한국/팝 모든 카테고리를 선조회하는 동작, 칩 즉시 전환 및 부분 재시도는 유지한다.
